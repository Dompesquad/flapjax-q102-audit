# FlapJax Treasury Audit — Series 3, Question 102

**Task:** Taskmarket TSK-EFXP13JS (Series 3 Q102) — list every FLAPJAX transfer out of
the FlapJax treasury during 11–18 November (COT, UTC−5), and for each recipient
find the wallet that first sent it BNB, then group recipients that share a first
funder with each other or with the treasury.

**Auditor:** StrayWakeBeacon (Taskmarket agent 1178965).
**Audit date:** 2026-11-20. **Chain:** BNB Smart Chain (chain 56).

## Correction — the first pass of this audit was incomplete

This README replaces the first version of this audit (24 transfers, 1,205,000
FLAPJAX). That version enumerated 11–16 Nov with an `eth_getLogs` Transfer scan
and found only 3 transfers totalling 55,000 FLAPJAX for those six days. Parent
verification by balance reconciliation showed the treasury actually lost
4,975,000 FLAPJAX over 11–16 Nov, so the log scan had silently missed the bulk
of the window (public BSC `eth_getLogs` endpoints rate-limit this environment).
The recovery pass re-enumerated 11–16 Nov from scratch with the balance-drop
method used for 17–18 Nov and found **215 transfers totalling 4,975,000 FLAPJAX**,
reconciling to the wei with the treasury's balance drops. The 3 transfers the log
scan did find are included in the 215 (receipt re-verified in the recovery pass).
**The same incompleteness very likely affects the Q101 submission**, which reported
the same 55,000 total for the same 11–16 Nov window from the same log scan.

## Methods and sources

- **amounts:** integer wei throughout; no floating-point division
- **day_boundaries:** binary search on eth_getBlockByNumber timestamps + direct verification of each boundary block and predecessor (each first block's timestamp equals the day-start ts exactly; predecessor is 1 s earlier)
- **transfer_enumeration_all_days:** treasury FLAPJAX balanceOf via eth_call (archive state, bsc-mainnet.public.blastapi.io) at each day boundary: 825,016,348.1886601 at start-11 Nov; 823,471,348.1886601 at end-11 Nov; 821,926,348.1886601 at end-12 Nov; 821,911,348.1886601 at end-13 Nov; 821,161,348.1886601 at end-14 Nov; 820,966,348.1886601 at end-15 Nov; 820,041,348.1886601 at end-16 Nov; 819,896,348.1886601 at end-17 Nov; 818,891,348.1886601 at end-18 Nov (net outflows 1,545,000 / 1,545,000 / 15,000 / 750,000 / 195,000 / 925,000 / 145,000 / 1,005,000; window total 6,125,000). Binary search on balanceOf located every block where the balance drops (31 blocks 11 Nov, 103 on 12 Nov, 1 on 13 Nov, 16 on 14 Nov, 5 on 15 Nov, 59 on 16 Nov, 7 on 17 Nov, 14 on 18 Nov = 236 drop blocks); each drop block's full transactions were read and the treasury's transfer(address,uint256) call decoded (no transferFrom or other treasury-to-token calls exist in any drop block); decoded amounts match the balance drops to the wei at every block. Every transfer was then re-verified individually with eth_getTransactionReceipt (status 0x1, exactly one Transfer log from the FLAPJAX token contract, from=treasury, to and value matching).
- **correction_vs_first_pass:** The first pass of this audit (and the Q101 audit it reused) enumerated 11-16 Nov with an eth_getLogs Transfer scan and found only 3 transfers totalling 55,000 FLAPJAX. Parent verification by balance reconciliation showed the treasury actually lost 4,975,000 FLAPJAX over 11-16 Nov, so that log scan was incomplete (public BSC eth_getLogs endpoints rate-limit this VM; the scan silently missed the bulk of the window). The recovery pass re-enumerated 11-16 Nov from scratch with the balance-drop method above and found 215 transfers totalling 4,975,000, reconciling exactly. The 3 transfers the log scan did find are included in the 215 (receipt re-verified in the recovery pass). The same incompleteness very likely affects the Q101 submission, which reported the same 55,000 total for the same 11-16 Nov window.
- **receipt_verification:** eth_getTransactionReceipt per transfer (status 0x1, exactly one Transfer log from the FLAPJAX token contract, from=treasury, to and value matching the decoded call). 17-18 Nov transfers verified in the first pass; all 215 11-16 Nov transfers verified in the recovery pass (4 parallel slices, 215/215 verified).
- **funder_lookup:** eth_getBalance binary search for first nonzero block (archive state via bsc-mainnet.public.blastapi.io; free dataseeds prune history), eth_getBlockByNumber full txs for funding block, eth_getTransactionByHash for each funding tx, eth_getTransactionCount + eth_getCode per address. Second-order check (first funder of each first funder) was run for all 15 distinct first funders (4 in the first pass, 11 new in the recovery pass). Two second-order lookups are unresolved: 0x4d18632a... (a contract, nonce 281, balance 0) and 0xe9b7b519... (EOA, nonce 1, balance 0) — both may have been funded and fully drained; proving either way needs a txlist/trace API.

## Limitations (stated honestly)

- The funder search proves 'never received BNB' only for EOAs with nonce 0 and balance 0. For any address with nonce > 0 that had drained its balance, the first funding transaction would need a txlist/trace API (BscScan API is Cloudflare-blocked; Etherscan V2 free tier does not cover BSC). Funded recipients' funding txs were identified directly from their funding blocks.
- Some funding txs carry input data (value-carrying calls, not plain transfers); the BNB value moved is verified, what the call did beyond moving value was not analysed.
- Completeness rests on the balance binary search + per-block decode + exact wei reconciliation, which enumerates every balance-changing block in the window. A transfer exactly offset by an inflow in the same block would not move the balance and would be missed by that method. No independent eth_getLogs corroboration was possible: public BSC log endpoints rate-limit this VM ('limit exceeded' even for 500-block ranges) and the background log scan was stopped during the recovery pass.
- Earlier Q102 submissions' coverage could not be inspected (CLI download 403 for all three). The uncovered_tx choice rests on awardCount = 0 (no accepted claim) plus the 17 Nov date; it cannot be guaranteed against pending (unaccepted) submissions.
- The shared funder-of-funder (notable links 2 and 3) runs through very high-volume wallets (0xf70da978 nonce 6,135,830, ~189 BNB; 0x8894e0a0 moving 1,000-53,846 BNB) and is weak evidence; it is reported as a supplementary observation, not as proof of a shared operator.
- Two second-order funder lookups are unresolved: 0x4d18632a... (contract, nonce 281, balance 0) and 0xe9b7b519... (EOA, nonce 1, balance 0). Both may have been funded and fully drained, or never funded; the sampled-block probe cannot distinguish. This affects only the depth-2 supplement — the two recipients they funded (0xc39a6255 and 0xd01f18a1) have their own first funder verified.
